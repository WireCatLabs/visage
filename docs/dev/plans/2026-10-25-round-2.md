## 2. Logs (no open decision)

Source: each installed tool's own `runs list --json` and `runs show <id> --json`, with no profile word, for all six
tools. The CLI normalises old and new record shapes; the app never parses `events.jsonl` itself. A zm, drive or memo
from before its `runs` commands refuses with "unknown command"; the Logs page says its logs arrive with the next
update of that tool instead of showing an error. Keeping every run is offered only where the catalog has a defaults
layer and `config unset` (tg, max, wa), since turning it back off removes the setting.

Screen, in the Datadog spirit:

- Query bar with the WireCat query syntax (`status:failed command:sync*`), field autocomplete.
- Facet column: counts per value for tool, status, command, error code, profile; click to filter, Alt-click to exclude.
- Table: time, tool, profile, command, status, duration, error code. Group by any facet field to see counts.
- Row expands to the run's events and a collapsible JSON tree; "Filter by this value" on any leaf.
- Everything shown passes `redact.rs` first.

Rust: `list_runs(tool, query, page)` and `show_run(tool, run_id)`, both mapped to the fixed CLI commands, `run_id`
validated like a profile name.

not installed" with Install or Update for that one cell.

## 4. Storage explorer (NEED-4)

Facts: one shared database (`wirecat.db`, schema 29, WAL). `tg store info --json` gives totals in 0.1 s. No command
gives breakdowns by messenger, account or chat type. Per-table sizes take 39 s, so they are never live.

Screen: a "What is in the archive" block above the folder list: totals (chats, messages, emails, documents,
meetings, attachments), then a breakdown chooser (by messenger · by chat type · by account · by year) as a small bar
table. Folders get a "what this is" line per known file kind (sessions are credentials, shown by size only).

## 6. Bug reports (NEED-6)

Desktop: a form (what happened, what you expected), a preview of exactly what becomes public (the issue text,
versions, OS) and what stays private (redacted logs), then the issue link.

Server: the first server-side WireCat component. Proposed: a Cloudflare Worker (Hono) at `api.wirecat.dev`, R2 for
private logs with a 90-day delete rule, a GitHub App with Issues write on `WireCatLabs/visage` only, per-IP rate
limit, size limit, a second redaction pass. Needs new secrets and a privacy-policy paragraph.

## 8. Config (NEED-7)

Asked mid-round: "manage configs via a separate menu item visually and via json editing (similar to what vscode
allows)".

Facts: tg, max, wa, zm and drive have `<bin> <profile> config show --json` (each setting, its value, and where it came
from: default, defaults file, profile, environment) and `config set` / `config unset`, which validate the value.
`--defaults` changes what every profile gets. memo's config command is still to check.

Screen, like VS Code settings: tool and profile picker (every profile listed, none chosen for the owner), then a
**Settings** tab (one row per setting: name, value control by type, "from" badge, reset) and a **JSON** tab (the
settings as JSON in an editor with syntax colouring, validation messages inline). Saving the JSON tab turns the diff
into `config set` / `config unset` calls, so the CLI checks every value; the app never writes the file itself.
